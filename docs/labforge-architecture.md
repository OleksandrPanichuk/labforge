# LabForge — система автоматизації лабораторних робіт

**Статус:** архітектурна дока / RFC
**Дата:** 2026-08-15
**Режим роботи:** локально (старий ноут, ~16 год/добу), доступ ззовні через tunnel

---

## 1. Ідея одним абзацом

Юзер закидає файл з вимогами до лабораторної (через Telegram-бота або веб-чат). Система, працюючи на Claude-підписці через Agent SDK, збирає контекст (методички, вимоги викладача/предмету, схожі лаби), пише і верифікує код у ізольованих Docker-контейнерах, генерує проміжний формат опису звіту (IR — intermediate representation), рендерить його як HTML-превʼю, що виглядає як docx, з інтерактивними поясненнями кожного факту і числа. Після рев'ю людиною IR конвертується в docx за ДСТУ + генерується md-файл підготовки до захисту. Юзер отримує: **весь код лаби + звіт (.docx) + пояснення/підготовку до захисту (.md)**.

## 2. Ключове архітектурне рішення: робота через підписку

### 2.1 Що ти пропонував і чому це не потрібно

Ідея "тримати відкриту сесію, яка слухає логи і по запиту активує сабагента" — це спроба збудувати IPC поверх інтерактивного UI. Це крихко, недетерміновано і не потрібно, бо існує офіційний механізм.

### 2.2 Як правильно: Claude Agent SDK

**Claude Agent SDK** (`@anthropic-ai/claude-agent-sdk`, TypeScript) — це бібліотека, на якій побудований сам Claude Code. Вона дає програмний доступ до того самого агентного циклу:

- `query({ prompt, options })` — запуск агентної сесії з коду. Повертає async-ітератор повідомлень (assistant messages, tool calls, results).
- **Аутентифікація через залогінений Claude Code CLI** на цьому ж ноуті (`claude login` один раз). Жодних API-ключів. Використання йде з лімітів підписки.
- **Session ID + resume** — кожна сесія має ID, її можна відновити (`resume: sessionId`) і докинути нове повідомлення. Це основа для (а) питань юзеру посеред роботи, (б) продовження після вичерпання лімітів.
- **Subagents** — декларуються в `options.agents` або як `.claude/agents/*.md` файли; головна сесія делегує їм через Task tool. Кожен сабагент має свій контекст, свій системний промпт, свій набір дозволених тулів.
- **Hooks** (PreToolUse/PostToolUse/Stop тощо) — детерміновані перехоплення: логування, заборона певних команд, checkpoint після кожного етапу.
- **allowedTools / permissionMode** — жорсткий контроль, що агенту можна: `Read, Write, Bash(docker run:*)` і так далі.
- **canUseTool callback / MCP custom tools** — можна дати агенту тул `ask_user(question)`, який твій бекенд перетворює на повідомлення в Telegram і чекає відповіді.

Тобто твоя "головна сесія, що слухає" перетворюється на **звичайний BullMQ worker**, який на кожну задачу викликає `query()`. Проблема "щоб головна сесія знову не запустила підсесію" зникає повністю — оркестрація живе в твоєму коді (NestJS), а не в промптах.

Альтернатива без SDK — сирий headless-режим: `claude -p "prompt" --output-format stream-json --resume <id>`. Працює так само (SDK — це обгортка над ним), корисно для дебагу руками.

Дока далі написана так, щоб перехід 1 → 2 був зміною конфігурації, а не архітектури.

## 3. Загальна архітектура

```
┌────────────┐   deep link    ┌──────────────────────────────┐
│ Telegram    │──────────────▶│ Web App (TanStack Start)      │
│ bot (grammY)│               │ чат + HTML-превʼю звіту        │
└─────┬──────┘               │ side panels, SSE live updates  │
      │ webhook/polling       └──────────────┬───────────────┘
      ▼                                      │ HTTP/SSE
┌─────────────────────────────────────────────▼──────────────┐
│ Backend: NestJS (моноліт, monorepo pnpm+turborepo)          │
│  ├─ Auth (tg id) ├─ Labs API ├─ Reports API ├─ SSE hub      │
│  ├─ BullMQ queue "labs" (concurrency: 1)                    │
│  └─ Orchestrator service ──▶ Claude Agent SDK query()       │
│                               (auth: локальний claude login)│
└───────┬─────────────────────────────┬───────────────────────┘
        │                             │
        ▼                             ▼
┌───────────────┐            ┌─────────────────────────┐
│ PostgreSQL     │            │ Docker sandbox           │
│ (JSONB) + Redis│            │ (dockerode, no network,  │
└───────────────┘            │ cpu/mem/time limits)      │
                              └─────────────────────────┘
Файлова система (git-репо):
  /kb        — knowledge base (per subject/lab, checkpoint-файли)
  /configs   — REQUIREMENTS.md / STYLE_GUIDE.md ієрархія
  /data      — існуючі лаби, розпаршені методички (md)
  /jobs/<id> — робоча директорія кожної лаби (код, IR, артефакти)
```

**Чому Postgres (JSONB), а не окрема NoSQL.** Твій інстинкт "JSON зберігати в самий раз" — правильний, але Mongo додає ще одну систему на слабкий ноут заради нуля переваг: Postgres JSONB зберігає ті самі документи (IR звіту, explanations, конфіги), а users/jobs/queue-стан — це таки relations. Ти вже знаєш Prisma+Postgres, Redis і так потрібен для BullMQ. Одна база менше = менше RAM, менше опсів. Якщо принципово хочеться document-store — Mongo підходить, але це усвідомлена ціна, не виграш.

## 4. Ієрархія конфігурацій (вимоги + стилі)

Структура (твоя, формалізована):

```
/configs
  REQUIREMENTS.md              # базові вимоги до всіх лаб/коду/звіту
  STYLE_GUIDE.md               # базове оформлення звіту (шрифти, без заливок і т.д.)
  subjects/
    <subject-slug>/
      REQUIREMENTS.md          # опційно
      STYLE_GUIDE.md           # опційно
  teachers/
    <teacher-slug>/
      REQUIREMENTS.md          # опційно
      STYLE_GUIDE.md           # опційно
      subjects/<subject>/...   # опційно: викладач X саме по предмету Y
```

**Резолюція (пріоритет: викладач > предмет > база):** для кожного з двох типів файлів береться найспецифічніший існуючий; якщо у викладача є тільки STYLE_GUIDE — вимоги беруться з рівня предмету або бази. Резолвер — детермінований TypeScript-код (не агент!), який на вході отримує `{subject, teacher}` і повертає два фінальні шляхи + пише resolved-копії в `/jobs/<id>/context/`. Агент читає вже готове.

**Рекомендація:** merge-семантика замість чистого override. Тобто фінальний файл = база + предмет + викладач, конкатеновані з заголовками "Базові вимоги / Вимоги предмету / Вимоги викладача (найвищий пріоритет, при конфлікті переважають)". Інакше файл викладача доведеться дублювати всім базовим текстом. Конфлікти хай розрулює агент за явним правилом пріоритету, написаним у шапці.

Кожен конфіг — з frontmatter (`teacher: Іваненко`, `aliases: [іваненко, ivanenko]`), щоб агент-оглядач міг зіставити ім'я з файлу лаби з наявними конфігами без вгадування.

## 5. Проміжний формат звіту (Report IR)

Це найважливіший контракт системи: **агенти пишуть IR, рендерери (HTML і docx) його читають.** Один source of truth → превʼю і docx не розʼїжджаються.

### 5.1 Схема (JSON)

```jsonc
{
  "version": 1,
  "meta": {
    "labId": "...", "subject": "...", "teacher": "...",
    "title": "Лабораторна робота №4 ...",
    // ПІБ/групу/варіант бере збірка з configs/student.json, не агент
    "student": { "name": "...", "group": "...", "variant": "7" },
    "language": "uk"
  },
  "page": {                        // A4 і поля з STYLE_GUIDE
    "size": "A4",
    "marginsMm": { "top": 20, "right": 10, "bottom": 20, "left": 20 },
    "pageNumbers": true
  },
  "styles": {                      // named styles, з resolved STYLE_GUIDE
    "default":   { "font": "Times New Roman", "size": 14, "lineHeight": 1.5, "align": "justify", "firstLineIndent": "1.25cm" },
    "heading1":  { "size": 14, "bold": true, "align": "center", "caps": true },
    "caption":   { "size": 12, "align": "center" }
  },
  // id обовʼязковий у кожного блоку (^blk_): по ньому адресуються правки з рев'ю
  "blocks": [
    { "id": "blk_goal", "type": "heading", "level": 1, "style": "heading1", "text": "МЕТА РОБОТИ" },
    { "id": "blk_intro", "type": "paragraph", "style": "default",
      "text": "Метод Рунге-Кутти 4-го порядку має локальну похибку <span data-x=\"e1\">O(h^5)</span>, що підтверджено обчисленням: максимальна абсолютна похибка склала <span data-x=\"c1\">{{v:err_max}}</span>." },
    { "id": "blk_rk4", "type": "formula", "latex": "y_{n+1} = y_n + \\frac{h}{6}(k_1 + 2k_2 + 2k_3 + k_4)", "numbered": true },
    { "id": "blk_results", "type": "table", "style": "default", "caption": "Таблиця 1 — Результати",
      "header": ["x", "y точне", "y обчислене", "похибка"],
      "rows": [["{{v:x0}}", "{{v:ye0}}", "{{v:yc0}}", "{{v:d0}}"]] },
    { "id": "blk_plot", "type": "image", "src": "artifacts/plot_convergence.png",
      "caption": "Рисунок 1 — Збіжність методу", "width": "80%",
      "provenance": { "kind": "generated", "codeRef": "cells/plot_convergence.py" } },
    { "id": "blk_src", "type": "code-listing", "language": "python", "file": "src/runge_kutta.py", "lines": [1, 40] },
    { "id": "blk_steps", "type": "list", "ordered": true, "items": ["...", "..."] },
    { "id": "blk_break", "type": "pagebreak" }
  ],
  "values": {                      // ЗАПОВНЮЄТЬСЯ ТІЛЬКИ виконанням коду, не агентом
    // агент пише лише cellRef+format; value і runRef додає resolver
    "err_max": { "value": "3,20e-6", "cellRef": "cells/compute_errors.py", "format": "sci:2",
                 "runRef": "runs/cells-compute-errors-py.json" },
    "x0": { "value": "0,1", "cellRef": "cells/compute_table.py" }
  },
  "explanations": {
    "e1": { "type": "text", "html": "Порядок точності випливає з розкладу Тейлора…",
            "sources": [{ "title": "Butcher, Numerical Methods for ODEs", "url": "https://doi.org/10.1002/9780470753767" }] },
    "c1": { "type": "code", "codeRef": "cells/compute_errors.py",
            "note": "Значення отримано виконанням цього коду в контейнері" }
  }
}
```

Джерело істини схеми — `packages/ir/src/schema.ts`; приклад вище лише ілюструє її.

Inline-розмітка в `text` — обмежений HTML-сабсет: `<b> <i> <u> <sub> <sup> <span data-x="id">`. Рендерери валідують білим списком (sanitize), все інше ріжеться.

### 5.2 Верифіковані числа — головна анти-галюцинаційна механіка

Це те, що ти вже прототипував, і це треба зробити **жорстким інваріантом**: агенту заборонено (промптом + валідатором) писати числові результати текстом. Кожне обчислюване значення — тільки плейсхолдер `{{v:key}}`, а `values` заповнює **resolver**: детермінований крок, який виконує computation cells у Docker-контейнері, кожна cell друкує JSON `{key: value}` в stdout, resolver збирає, форматує (`sci:2`, `fixed:4`, локаль з комою) і підставляє.

Наслідки:
- Число в звіті фізично не може бути вигадане — воно або з коду, або збірка падає з помилкою "unresolved value".
- **Review-агенту не треба переперевіряти цифри LLM-ом** (найдорожча за токенами частина твого циклу!) — коректність чисел гарантується виконанням. Рев'ю перевіряє логіку коду, а не арифметику.
- Кожне число автоматично має provenance для explanation-панелі — задарма.

### 5.3 Computation cells і дедуплікація коду

Твоя вимога: фінальний код = чистий код лаби, без сміття "надрукуй проміжну цифру для звіту", і без дублів логіки. Рішення:

```
/jobs/<id>/
  src/                 # чистий код лаби — те, що здається викладачу
  cells/               # тонкі обгортки для звіту: import із src/, обчислюють
                       # конкретні values/графіки, друкують JSON / зберігають png
  artifacts/           # png графіків, скріншоти
  report.ir.json
  runs/                # логи виконань (для provenance)
```

Правило для агента: **cells імпортують функції з `src/`, а не копіюють їх.** Тоді дублів логіки нема за конструкцією, а `src/` лишається чистим. Це і є твоє "код для цифр не включати в загальний код" — він просто живе в окремій директорії, яку юзер може дивитись опційно (через explanation-панель), але вона не частина здачі.

## 6. HTML-превʼю звіту

### 6.1 Рендеринг "як docx"

- Рендерер IR → HTML: React-компонент на блок-тип. Стилі мапляться з `styles` IR.
- **Пагінація на A4-сторінки: [Paged.js](https://pagedjs.org/)** — CSS Paged Media полифіл, дає справжні сторінки з полями (ДСТУ: 20/10/20/20 мм), номерами сторінок, розривами. Без нього "виглядає як docx" не вийде — звичайний HTML не пагінується. Це найважливіша лібка для фронту превʼю.
- Формули: **KaTeX** (швидший за MathJax, рендерить LaTeX синхронно).
- Шрифт: Times New Roman локально є на маках; для інших — метрично сумісний Liberation Serif як fallback (у docx все одно піде справжній TNR).

### 6.2 Інтерактивність

- `<span data-x="id">` рендериться з `border-bottom: 1px dotted` + hover. Клік → бокова панель:
  - **type=text:** пояснення + обовʼязкові посилання на джерела (якщо джерел нема — рендерер показує бейдж "без джерела", а report-review-агент має правило це флагати).
  - **type=code:** CodeMirror 6 read-only (легший за Monaco, важливо для старого ноута) з кодом cell. Кнопка **Run** → POST `/api/jobs/:id/cells/:cell/run` → виконання в Docker → stdout/результат у панелі. Кнопка **Спитати ШІ** / виділення фрагмента коду → чат-тред, привʼязаний до `codeRef` + selection range.
- **Виділення будь-якого фрагмента звіту** (слова, абзаци, таблиці, зображення) → floating toolbar "Обговорити з ботом" / "Це неправильно". Технічно: selection → мапиться на `blockId + offset range` (кожен блок IR має стабільний `id`), у бекенд летить `{blockIds, quotedText, userMessage}` — цього достатньо, щоб агент знав контекст, не отримуючи весь звіт.
- **Зображення:** hover → меню з двох пунктів: "Спитати бота" і "Відкрити код" (якщо `provenance.kind === "generated"`, відкриває cell у тій самій код-панелі; юзер коментує → fix-агент править cell → cell перезапускається → png оновлюється → SSE-подія → `<img>` перерендерюється).
- **Live-оновлення:** SSE (простіше за WebSocket, вистачає — трафік односторонній: сервер → браузер). Події: `ir.updated`, `value.resolved`, `image.updated`, `job.status`, `agent.question`.

### 6.3 Цикл правок після рев'ю юзера

Юзер коментує → задача "revision" в чергу (поза глобальною one-at-a-time чергою нових лаб, бо це та сама лаба) → resume агентної сесії з контекстом `{коментар, blockIds, quotedText}` → агент патчить **IR, а не HTML** → resolver перезбирає values, якщо зачеплені → SSE → превʼю оновилось. Патчі до IR — точкові (по block id), щоб не переписувати весь документ (і токени, і скачки UI).

## 7. Зображення і графіки

Три джерела, як ти описав, з уточненнями:

1. **Генеровані кодом** (графіки, діаграми): matplotlib/plotly у cell, зберігає png (300 dpi для docx) в `artifacts/`. Provenance = codeRef. Це основний шлях.
2. **Скріншоти працюючої апки/GUI:** не "агент запустить на моєму компі і зробить скрін" — це крихко і небезпечно. Замість цього: **у контейнері**. Для веб-апок — Playwright headless screenshot. Для десктопних GUI (якщо раптом лаба на tkinter/Qt) — контейнер з Xvfb + `import` / скріншот віртуального дисплея. Хост-машина не чіпається взагалі.
3. **З інтернету:** пошук картинки агентом (WebSearch/WebFetch тули SDK), збереження локально, provenance = `{kind: "web", url, retrievedAt}`. Рендерер підписує джерело під рисунком (і для доброчесності, і бо викладачі це люблять).

## 8. Генерація docx

- Вхід — той самий IR. Генератор — детермінований TypeScript на бібліотеці **`docx`** (ти нею вже користувався для ДСТУ-прототипу): стилі IR → docx styles, blocks → Paragraph/Table/ImageRun, pagebreak → PageBreak, поля/титулка за STYLE_GUIDE.
- **Формули:** найболючіше місце docx-генерації. Шлях: LaTeX → MathML (**temml**, легка лібка) → OMML (офіційний XSLT `MML2OMML.XSL` від Microsoft, або lib `mathml2omml`) → вставка як Math-елемент. Fallback, якщо конкретна формула не конвертується: рендер KaTeX → SVG → PNG 300dpi → ImageRun (виглядає ок, не редагується в Word — прийнятний компроміс).
- **Агент-перевірка docx:** ти пропонував агента, що звіряє "чи docx відповідає IR". Дешевше: конвертер детермінований, тому одноразово покривається **golden-тестами** (fixture IR → очікуваний docx XML), а на кожну лабу ганяти LLM-звірку не треба. Залишити LLM-звірку як опційний прапорець `--paranoid` для перших тижнів: docx → розпакувати XML / extract text → порівняти з IR текстом diff-скриптом (навіть це можна без LLM).

## 9. Файл підготовки до захисту (.md)

Генерується окремим агентом після затвердження звіту. Контекст (як ти і сказав): resolved вимоги, повний `src/`, всі cells з їх значеннями, IR звіту. Структура:

1. Короткий переказ: що робилось і навіщо (2–3 абзаци, "розкажи своїми словами").
2. Пояснення коду по файлах/функціях: що робить, чому саме так.
3. Пояснення кожної формули: звідки береться, що означає кожен символ.
4. Пояснення кожного графіка/таблиці: що на ньому видно, який висновок.
5. Типові питання викладача + відповіді (генеруються з вимог + методички; якщо в конфігу викладача є секція "улюблені питання" — з неї в першу чергу).
6. Слабкі місця: чесний список того, що можуть підловити ("чому крок 0.1, а не 0.05?").

## 10. Агентний цикл

### 10.1 Твій флоу (зафіксований, з мапінгом на SDK)

Оркестрація — **стейт-машина в NestJS**, а не "начальник-агент". Стани: `CONTEXT → CLARIFY → SOLVE → CODE_REVIEW → FIX → IR_WRITE → REPORT_REVIEW → HUMAN_REVIEW → REVISION → BUILD → DEFENSE_PREP → DONE`. Кожен перехід = checkpoint (див. §11). "Начальник" як LLM потрібен лише для рішень, що вимагають судження ("чи findings ще варто фіксити?"), — і навіть це можна зробити правилом (див. нижче).

Ролі (сабагенти SDK, кожен зі своїм промптом і allowedTools):

1. **Scout (оглядач):** збирає контекст. Читає файл лаби → витягує предмет/викладача → резолвить конфіги (детермінований код, не він) → читає розпаршену методичку з `/data/parsed/` → шукає схожі лаби в `/data/labs/` → гуглить незнайомі терміни (WebSearch) → **питає юзера** через тул `ask_user` про те, що не можна знайти (слова викладача, варіант, вихідні дані). Результат — один файл `context.md` в job-директорії. Сесія на час питання **паузиться** (session ID зберігається, worker звільняється), відповідь юзера з TG/веб — resume.
2. **Solver (виконавець):** пише весь код лаби в `src/` за `context.md` + вимогами. Зобовʼязаний написати і **самоперевірку**: мінімальні тести / звірку з відомими значеннями з методички, і прогнати в Docker до передачі далі.
3. **Code reviewer:** інструкція "не довіряти нічому" зберігається, але звужується: **числа не перевіряє** (їх гарантує resolver + тести Solver-а), перевіряє: покриття всіх пунктів завдання (чек-лист із context.md), відповідність вимогам, логічні баги, крайові випадки. Кожен finding — `{severity, file, line, why, suggestedFix}` — саме з причиною, як ти хотів, щоб fix-агент не шукав.
4. **Fixer:** отримує тільки findings + зачеплені файли (не весь контекст!). Після фіксу — reviewer знову, з попередніми findings у контексті.
   **Стоп-правило замість "начальник вирішить":** максимум 3 цикли АБО не лишилось findings severity ≥ major АБО два цикли поспіль однакові findings (зациклення → ескалація юзеру). Це детермінований код — нуль токенів на "менеджерські" рішення.
5. **Report writer:** пише IR. Контекст: context.md + вимоги/стилі + `src/` (без findings — правильно, вони йому не потрібні). Створює cells для кожного значення/графіка (сам, без під-сабагентів — cells тонкі, окремий агент на кожен — це overhead; якщо cell падає, він же і чинить). Після написання — resolver проганяє всі cells, unresolved values = блокер.
6. **Report reviewer (інший тип):** стиль, повнота секцій за методичкою, вимоги викладача, наявність джерел у text-explanations, ДСТУ-оформлення. Findings → Report writer → цикл, те саме стоп-правило (2 цикли зазвичай досить).
7. **Людина** (превʼю, §6.3), потім **Build** (детермінований: docx + фінальна перевірка), потім **Defense prep** агент (§9).

### 10.2 Дешевші альтернативи (по зростанню економії)

Твій флоу правильний за формою, але в максимальній версії — це 6–8 LLM-сесій на лабу з перетинним контекстом. Де різати токени:

**A. Детермінізація менеджменту (вже вшито вище, ~безкоштовно).**
"Начальник" → стейт-машина + стоп-правила. Економія: 1 постійно висяча сесія з великим контекстом зникає повністю. Це найбільший виграш і він не погіршує якість.

**B. Верифікація виконанням, не читанням (вже вшито, велика економія).**
Найдорожче в твоєму циклі — reviewer, що "в кожному числі має впевнитися". LLM-перевірка чисел і дорога, і ненадійна. Resolver + тести Solver-а роблять це виконанням коду: точно і за нуль токенів. Reviewer лишається для логіки.

**C. Model mixing (легко, помітна економія лімітів).**
SDK дозволяє задати модель на сабагента: Solver і Report writer — топ-модель; Scout, reviewers, Fixer, Defense prep — Sonnet; дрібні механічні кроки (форматування findings, витяг предмету з файлу) — Haiku. На підписці це подовжує ліміти в рази.

**D. Стислий флоу "3 сесії" (середня лаба, −50–60% токенів).**
Для типових лаб обʼєднати ролі: (1) Scout+Solver одна сесія — контекст свіжий, без переливання через файл; (2) Reviewer+Fixer одна сесія — знайшов→одразу фіксить, самоціль "незалежного рев'ю" тут переоцінена, бо коректність чисел і так гарантована resolver-ом; (3) Report writer + report review як self-review checklist у тому ж промпті. Повний флоу з §10.1 вмикати прапорцем для складних/нових предметів.

**E. Кешування знань між лабами (кумулятивна економія).**
`/kb/<subject>/notes.md` — після кожної лаби Defense prep-агент дописує туди: специфіку викладача, формат звітів, граблі. Scout наступної лаби по цьому предмету читає notes.md замість повторного гугління і повторних питань юзеру. Лаба №5 по предмету стає радикально дешевшою за лабу №1.

**F. Одноразовий препроцесинг (ти вже запланував — підтверджую).**
Методички PDF → md конвертяться один раз офлайн-скриптом (не в циклі лаби), старі лаби — так само, з коротким `summary.md` на кожну (Scout спершу читає summary, повну лабу — тільки якщо релевантна).

**Рекомендація:** MVP = флоу D + правила A, B, F. Повний флоу §10.1 — як "hard mode" для перших лаб нового предмету/викладача, поки не наповниться `/kb`.

## 11. Checkpoints, ліміти, відновлення

- Після кожного стану стейт-машини в `/jobs/<id>/checkpoint.json` пишеться: стан, session IDs всіх причетних сесій, шляхи артефактів, findings, лічильники циклів. Job-директорія — у git-репо (комміт на checkpoint) → історія + відкат безкоштовно.
- **Вичерпання лімітів:** SDK-виклик повертає помилку rate limit → worker ловить → job у стан `PAUSED_RATE_LIMIT` → юзеру в TG "ліміти вичерпано, продовжу о ~HH:MM" (час резету видно в повідомленні про ліміт) → BullMQ delayed job на цей час → resume сесії з того ж місця (`resume: sessionId`). Якщо сесія не відновлюється (протухла) — рестарт поточного стану з checkpoint-артефактів: саме тому кожен стан має на вході файли, а не "памʼять попередньої сесії".
- **Ноут вимкнули на ніч:** BullMQ у Redis з AOF-персистентністю — черга переживає ребут; при старті бекенд сканує jobs у проміжних станах і піднімає їх.

## 12. Черга і юзери

- BullMQ queue `labs`, **concurrency: 1** — твоє "one lab at a time" це буквально одна опція. Revision-задачі активної лаби і `ask_user`-відповіді йдуть поза цією чергою (вони частина поточного job).
- Позиція в черзі → юзеру в TG ("ти №3, перед тобою ~2 лаби").
- **Auth:** Telegram ID — первинний ідентифікатор (whitelist у конфігу). Бот генерує deep link на веб: підписаний короткоживучий токен (JWT, 15 хв) → сесійна cookie. Ніяких паролів. Юзер бачить тільки свої jobs.
- **TG-бот (grammY):** /start → whitelist-перевірка → "закинь файл лаби" → файл + опційний текст ("викладач Іваненко, варіант 7") → job створено → посилання на веб. Далі бот шле: питання від агентів (`ask_user`), зміни статусу, "звіт готовий до рев'ю", готові файли (docx + md можна прямо в TG, ліміт 50 МБ — вистачає).

## 13. Docker-пісочниця

- Керування через **dockerode** з NestJS. Запуск cell/коду: контейнер per-run, `--network none` (мережа тільки якщо лаба явно вимагає — окремий прапорець), `--memory 1g --cpus 1 --pids-limit 256`, timeout 120 с, non-root user, job-директорія монтується read-only + окремий writable `artifacts/`, tmpfs для /tmp.
- Заздалегідь зібрані образи: `lab-python` (numpy/scipy/matplotlib/pandas/sympy), `lab-node`, `lab-cpp` (gcc), `lab-playwright` (скріншоти), + Xvfb-образ для GUI. Агент обирає образ, не пише Dockerfile (окрім екзотики — тоді build з рев'ю).
- Агентам SDK доступ до Docker **тільки** через custom tool `run_in_sandbox(image, cmd, files)` — не сирий `Bash(docker …)`. Так у тебе один аудит-лог всіх виконань і неможливість `-v /:/host`.

## 15. Що ти не описав (і треба вирішити)

1. **Формат вхідного файлу лаби:** PDF? Фото дошки? docx? Потрібен ingest-пайплайн (PDF→md вже вмієш; фото → топ-модель читає нативно). Обмежити MVP: PDF + docx + txt/md.
2. **Ручні правки юзера в превʼю.** Зараз юзер може тільки просити бота. Чи можна юзеру самому виправити слово? Якщо так — правка має йти в IR (contentEditable на блоці → PATCH block), інакше її зітре наступний агентський патч. Рекомендую дозволити тільки text-правки, structure — через бота.
3. **Титульна сторінка:** ПІБ, група, номер варіанту, назва універу — це або в профілі юзера (задається раз), або питається щоразу. Додай у Postgres `user.profile`.
4. **Мова:** звіт українською, а коментарі в коді? Ідентифікатори? Задай у базовому REQUIREMENTS.md явно, інакше буде вінегрет.
5. **Скасування/зависання:** кнопка "скасувати" юзеру + watchdog: стан не змінювався 30 хв → alert тобі в TG.
6. **Прибирання диску:** артефакти + git-історія + docker layers на старому ноуті зʼїдять диск за місяць. Cron: контейнери — одразу, job-директорії DONE старші 30 днів — архів у tar.
7. **Скільки питань агент може задати юзеру:** без ліміту Scout буде спамити. Правило: максимум одне "питальне" повідомлення на стан, згруповані питання списком.
8. **Приватність між юзерами:** чужі лаби і kb по предмету — спільні чи ні? Kb — спільна (у цьому сенс), самі лаби — тільки свої.
9. **Резервне копіювання:** git-репо jobs/kb/configs → push у приватний GitHub щоночі; Postgres — pg_dump туди ж. Ноут старий — він помре, питання коли.
10. **Нумерація формул живе тільки в рендерері.** Номер `(N)` рахує рендерер під час
    збірки; в IR його нема. Наслідки: (а) посилання в тексті ("див. формулу (2)") ні до чого
    не привʼязані — вставка формули зсуне номери, а посилання лишаться старими; (б) превʼю
    і docx мусять порахувати однаково, інакше ламається критерій "превʼю збігається з docx".
    Рішення на майбутнє: винести нумерацію в окремий прохід над IR, спільний для обох
    рендерерів, або записувати номер у блок під час RESOLVE.
11. **Ноут і сон:** macOS/лінукс на ноуті з закритою кришкою спить → `caffeinate` / logind.conf `HandleLidSwitch=ignore`, і вентиляція, бо 16 год/добу під Docker — це піч.

## 16. Порядок реалізації (MVP → повна версія)

**Фаза 0 (1–2 вечори):** препроцесинг: скрипти PDF→md для методичок і старих лаб; структура /configs з базовими REQUIREMENTS/STYLE_GUIDE.
**Фаза 1 — ядро без веба (тиждень):** Agent SDK + стейт-машина + флоу D (3 сесії) + resolver + Docker-тул. Вхід — файл у папці, вихід — IR + docx у папці. Запуск CLI-скриптом. **Це вже робить лаби.**
**Фаза 2 — TG-бот + черга:** grammY, BullMQ, ask_user через TG, checkpoint/resume, ліміт-хендлінг.
**Фаза 3 — веб-превʼю:** TanStack Start, Paged.js рендер IR, explanation-панелі, run-cell, selection-чат, SSE.
**Фаза 4 — повний агентний цикл** (§10.1) як опція, defense prep, kb-накопичення, cloudflared.

## 17. Головні ризики

| Ризик | Мітигація |
|---|---|
| ToS при multi-user на підписці | MVP single-user; multi-user → API key (зміна env) |
| Ліміти підписки на важких лабах | model mixing (C), флоу D, checkpoint+resume, нічні запуски |
| Правила Anthropic для SDK/підписки знову зміняться | абстракція auth в одному місці; слідкувати за support-статтею 15036540 |

Відомий тригер: сирі `<` `>` `&` всередині `\text{}` — заборонено промптом report-writer. Якщо реальні лаби почнуть падати на цьому, повертаємо PNG-fallback (KaTeX→SVG→PNG) за тим самим error-path |
| Старий ноут (диск/перегрів/смерть) | нічні бекапи на GitHub, cleanup-cron, моніторинг температури |
| Розʼїзд превʼю vs docx | єдиний IR + golden-тести конвертера |
