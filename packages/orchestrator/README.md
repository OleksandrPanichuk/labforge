# @labforge/orchestrator

Стейт-машина, яка веде лабу від файлу завдання до готового звіту. Рішення — детермінований
код (інваріант 4), LLM живе тільки *всередині* станів, за портом `AgentRunner`.

```ts
const result = await runJob({ job, agents });
```

## Дві частини

`decide(checkpoint, outcome)` — чиста функція: поточний стан + результат агента → рішення
(`advance` / `pause` / `fail` / `finished`). Її можна читати як таблицю переходів і тестувати
без диска й без агентів.

`runJob` — драйвер: читає checkpoint, викликає агента, застосовує рішення через
`job.advanceTo` (тобто кожен крок одразу закомічений — інваріант 5), і зупиняється на
терміналі або паузі.

## Стоп-правила рев'ю-циклу

- Findings лише `minor` → цикл закінчено, йдемо далі.
- Максимум 3 проходи фіксера; далі — `PAUSED_WAITING_USER`, а не нескінченне коло.
- Ті самі findings двома раундами поспіль → теж пауза: цикл не збігається, і крутити його
  ще раз — це просто спалені токени.

Лічильники беруться з `checkpoint.cycles`, тому переживають перезапуск процесу, а порівняння
findings іде по `checkpoint.lastFindings[стан]` — **окремо для кожного циклу**: інакше id з
рев'ю коду (агенти люблять нумерувати `f0`, `f1`) збігалися б з id рев'ю звіту, і IR_FIX не
отримав би жодного шансу. Рішення приймається **до** запису нового раунду — інакше перший
же рев'ю виглядав би як повтор самого себе.

Коли цикл ескалюється, лічильник і збережені findings цього циклу скидаються: після відповіді
людини цикл має отримати нові спроби, а не ескалюватися одразу знову.

`FAILED` для драйвера — кінцевий стан: агент у ньому не викликається і повернутись у нього
не можна. Без цього job у `FAILED` при кожному retry робив LLM-виклик і міг нескінченно
коливатись між `FAILED` і `PAUSED_RATE_LIMIT`.

`CLARIFY` і `REVISION` не мають вхідних ребер у таблиці: у них job заводить зовнішній код
(веб-рев'ю у Фазі 3), а машина вміє їх коректно завершити.

## Паузи

`rate_limited` → `PAUSED_RATE_LIMIT` + `resumeAt` у checkpoint (звідти BullMQ бере затримку).
Така пауза розсмоктується сама: наступний запуск повертає job у `previousState`.

`needs_user` → `PAUSED_WAITING_USER` + питання, збережене в checkpoint (`question`).
Тут запуск НЕ продовжує job: без відповіді агент задасть те саме питання ще раз і так
по колу, тому `runJob` одразу повертає питання і виходить. Розблоковує його `recordAnswer`:
воно перевіряє, що job справді чекає, і кладе текст у `answer`. Наступний запуск передає
його рівно тому стану, який питав (`AgentRequest.answer`), і одразу забуває — щоб відповідь
не поїхала в усі наступні стани і не спливла при повторному прогоні. Відповідь іде в
prompt як дані студента, а не як інструкція, і має ліміт довжини.

`sessionIds[state]` зберігає id сесії, і продовження отримує його в `resumeSessionId` —
перевірено спайком, що SDK відновлює сесію навіть з іншого процесу.
