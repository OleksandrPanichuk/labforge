# @labforge/configs

Детермінований резолвер ієрархії вимог і стилів (docs/labforge-architecture.md §4).
Це код, а не агент: агент отримує вже готовий злитий файл.

```ts
const files = configFilesAt("configs");
const slug = findTeacherSlug("Іваненко", files);
const { requirements, styleGuide, sources } = resolveConfigs({ subject, teacher: slug }, files);
```

## Пріоритет

Від загального до специфічного, кожен наступний шар перекриває попередній:

```
REQUIREMENTS.md                                     # база
subjects/<subject>/REQUIREMENTS.md                  # предмет
teachers/<teacher>/REQUIREMENTS.md                  # викладач
teachers/<teacher>/subjects/<subject>/REQUIREMENTS.md  # викладач по предмету
```

`STYLE_GUIDE.md` резолвиться окремо і незалежно — у викладача може бути лише гайд стилів
без вимог. `sources` повертає список шарів, що реально брали участь: це те, що варто
покласти в `jobs/<id>/context/`, щоб потім було видно, звідки взялася кожна вимога.

## Merge, а не override

Замість заміни файли **конкатенуються** з підписами шарів і шапкою, яка явно каже, що при
конфлікті перемагає останній. Інакше файл викладача довелося б дублювати всім базовим
текстом. Frontmatter із вихідних файлів у результат не потрапляє.

## Пошук викладача

`findTeacherSlug` зіставляє ім'я з файлу лаби зі слугом директорії, полем `teacher:` або
списком `aliases:` у frontmatter — без урахування регістру. Тому "Іваненко", "ivanenko"
і "Іваненко І.І." ведуть в одну директорію, і Scout не мусить вгадувати.

Невідомий викладач — не помилка: резолвер просто не додає цей шар. Відсутність базового
`REQUIREMENTS.md` — помилка, бо без нього агент працює наосліп. Один і той самий alias
у двох викладачів — теж помилка (`ConfigError`), інакше вибір залежав би від порядку
читання директорії.

Імена нормалізуються через NFC + згортання пробілів, бо `subject`/`teacher` приходять із
тексту, витягнутого з PDF/docx, де регулярно трапляються decomposed-символи і NBSP.

## Безпека

`subject` і `teacher` витягує LLM із файлу лаби, тому це недовірений вхід. Два бар'єри:
zod-схема сегмента (літери/цифри/`._-`, жодних роздільників і `..`) і перевірка
входження в `configs/` у самому `configFilesAt`. Без них `subject: "../../secrets"`
підмонтував би довільний файл як шар з **найвищим пріоритетом** в інструкціях агента —
тобто і prompt injection, і читання чужих jobs (інваріант 8).

Тіла шарів проходять через екранування `<!--`, щоб файл не міг підробити маркер шару,
а самі маркери — позиційні (`## Layer 2 of 3`), їх не підробиш текстом.

## Хто автор звіту

`configs/student.json` — єдине джерело ПІБ, групи і варіанта:

```json
{ "name": "Прізвище І. П.", "group": "ІП-21", "variant": "7" }
```

`readStudentProfile` читає його на INGEST і кладе копію в `jobs/<id>/context/student.json`,
звідки report-writer зобов'язаний скопіювати `meta.student`. Варіант конкретної лаби
перекривається прапорцем `--variant`, бо він змінюється від роботи до роботи, а ПІБ і
група — ні. Збірка все одно проштамповує `meta.student` значеннями з файлу і додає
warning, якщо агент написав щось своє: особисті дані студента — це дані, а не вихід LLM.

Файл обов'язковий: без нього лаба падає ще до першого виклику агента з підказкою, що
створити. Це навмисно — інакше модель вигадає ПІБ і воно тихо поїде у docx.
Значення — один рядок без керуючих символів і з розумною довжиною, щоб ім'я не могло
підробити frontmatter чи розмітку файлів, куди його підставляють.

Реальний `configs/student.json` у git не потрапляє (`.gitignore`) — у репо лежить
`configs/student.example.json`.
